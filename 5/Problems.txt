Architecture Review & Remediation Document: OmniHealth Integration Platform


1. The Original Architectural Problems
The initial Azure deployment diagram (13627.jpg and 13433.jpg) presented a "Proof of Concept" (PoC) design rather than an enterprise-grade SaaS platform. The core flaws centered around network boundaries, security protocols, and multi-tenant isolation:
 * The Single-Network Illusion: The integration hub (Mirth, Azure API Management, Azure Functions) and the distinct hospital endpoints (OpenEMR-A, OpenEMR-B) were all placed inside the exact same Virtual Network (VNet) boundary.
 * IP-Based Routing: The system was designed to route traffic from Azure Functions to the downstream EMR applications using local IP addresses and ports rather than standard web protocols.
 * Ambiguous Component Roles: Azure API Management was placed in the center of the architecture, but it lacked clear external consumers or defined routing responsibilities.
 * Device Polling Constraints: Relying on a 1-to-1 local laptop configuration to listen to bedside monitors did not account for the massive scale required by hospital IoT telemetry (hundreds of beds).
 
 
2. The Architect's Critique (Saurabh's Feedback)
During the review, Saurabh (Senior Enterprise Architect) flagged several critical compliance and security issues that would prevent the architecture from passing an enterprise security audit.
 * Violation of Zero Trust Principles: Saurabh explicitly stated, "You have chosen virtual machine as a boundary, which is not right. Your boundary of isolation following the concept of zero trust should be a combination of identity and network." Placing two separate hospital clients (Hospital A and Hospital B) on the same network or isolating them merely by database schema is unacceptable in healthcare due to strict data segregation laws (HIPAA).
 * Insecure Integration Mechanisms: Saurabh completely rejected the IP-address routing approach, noting: "Its that design will not pass, Sir... There is no identity, there is no authorization involved. You are just going blindly by IP address. It is very, very easy to spoof it."
 * Identity Confusion (Host vs. Broker): The diagram made it appear as though the OmniHealth platform was hosting the hospital EMRs directly. Saurabh clarified that OmniHealth is a SaaS Integration Broker, meaning it must connect to externally managed hospital environments, not host them internally.
 * Lack of Standardized Security Handshakes: Saurabh noted that real-world hospitals will never expose internal IPs or accept unauthenticated traffic. They require secure, authenticated channels over the public internet.
 
 
3. Required Architectural Improvements
To transition the platform from a local demonstration to a production-ready, multi-tenant SaaS architecture, Saurabh mandated the following structural and security upgrades:
A. Implement the "Three-Silo" Isolation Model
The architecture must be visually and technically separated into three distinct boundaries to prove data segregation:
 * Data Producers: External bedside monitors, mobile apps, and IoT devices.
 * Integration Hub (OmniHealth VNet): The proprietary SaaS layer containing the Application Gateway, Mirth Connect, API Management, and Azure Functions.
 * Consumer Networks: Completely isolated, customer-managed environments (Hospital A Network and Hospital B Network) housing their respective EMRs and databases.
B. Mandate FQDNs over IP Addresses
Azure Functions must no longer attempt to reach local IP addresses. Instead, they must push data out to the hospitals using Fully Qualified Domain Names (FQDNs) (e.g., api.hospital-a.com), proving that traffic crosses deliberate network boundaries.
C. Enforce Identity & Access Management (IAM)
Before any Azure Function pushes data to a hospital's FQDN, it must authenticate.
 * The architecture must utilize Azure Key Vault to retrieve specific OAuth 2.0 tokens, Client IDs/Secrets, or TLS Certificates designated for that specific hospital client.
 * All traffic leaving the integration hub must be encrypted using TLS 1.2 or TLS 1.3.
D. Treat Bedside Telemetry as Scalable IoT


Instead of localized polling, the platform must treat incoming bedside monitor data as high-scale telemetry. Devices should push data securely through the Azure Application Gateway and WAF, allowing Mirth and Azure Blob Storage to handle the ingestion at an enterprise scale.
