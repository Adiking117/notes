The "Distributed Partial Failure" problem occurs when a single workflow spans across multiple independent systems (like two different hospital networks) where standard database transactions (like a SQL BEGIN/COMMIT) cannot be used.

What Would Have Happened If Ignored
Look closely at Task 8 (Cross-Hospital Patient Transfer). If you rely on a single Lambda script to handle the entire transfer, you expose the system to a catastrophic clinical mismatch.

Imagine this sequence:

FHIR_POST_LAMBDA reads the patient transfer bundle from the SQS queue.

It sends the POST request to Hospital B. Hospital B successfully admits the patient into their database and returns an HTTP 200 OK.

The Crash: At that exact millisecond, before your Lambda can delete the message from the SQS queue or notify Hospital A, the Lambda container experiences a network timeout or out-of-memory crash.

The Consequence: Because the SQS message was never deleted, SQS assumes the Lambda failed and re-delivers the exact same patient bundle 5 minutes later. Hospital B processes it again, creating a duplicate patient record. Meanwhile, Hospital A’s system still marks the transfer as "Pending/Failed". You now have a corrupted, out-of-sync clinical state across two different hospital networks.

How We Solved It (Architecture Integration)
We replaced the fragile single-Lambda script with an Orchestrated Saga Pattern using AWS Step Functions and an Idempotency Ledger.

The Saga Orchestrator (AWS Step Functions)

Instead of a single Lambda doing everything, SQS triggers a Step Functions State Machine. This breaks the transfer into isolated, trackable steps (e.g., Step 1: Push to Hosp B, Step 2: Ack to Hosp A, Step 3: Delete Staged File).

If Step 2 succeeds but Step 3 fails, the state machine does not restart from the beginning. It only retries Step 3. This guarantees Hospital B never receives the payload twice.

The Idempotency Ledger (Amazon DynamoDB)

To absolutely guarantee exactly-once processing, the State Machine first generates an Idempotency Key (a unique SHA-256 hash of the Patient_ID + Correlation_ID).

It writes this key to a DynamoDB table with a Time-To-Live (TTL) of 24 hours.

When making the API call to Hospital B, it passes this key in the header (X-Idempotency-Key). If a network glitch causes a retry, Hospital B's API checks the key, realizes it already processed this exact transfer 10 seconds ago, and safely returns a 200 OK without creating a duplicate database entry.

Compensating Transactions (Automated Rollbacks)

Because we cannot use a SQL rollback across two different hospitals, the Saga pattern uses Compensating Transactions.

If Step Functions pushes the data to Hospital B, but Hospital B's API rejects it (e.g., patient data validation fails), the State Machine automatically executes a "rollback" step. It triggers a callback to Hospital A's API to officially change the transfer status from IN_PROGRESS to FAILED_REJECTED, keeping both hospitals perfectly in sync.

Advantages
Guaranteed Data Integrity: It mathematically eliminates the risk of duplicate patient records and phantom data drops, even during catastrophic cloud outages.

Resilient Cross-Cloud Workflows: You can confidently orchestrate workflows that span across OmniHealth, Hospital A, Hospital B, and external APIs like Fitbit, knowing exactly where a failure occurred.

Auditability: AWS Step Functions provides a visual, step-by-step execution history. If a hospital disputes a transfer, you can pull up the exact state machine execution graph to prove exactly which API failed and when.

### Step 5: AWS Lambda Code (The Idempotency Lock)

This code goes into the `Saga-Task-Transfer-Hosp-B` Lambda. Before calling the hospital, it attempts to write a lock to DynamoDB. If the lock already exists (a retry from a previous timeout), DynamoDB mathematically rejects the write, and the Lambda gracefully skips the duplicate API call.

```python
import json
import boto3
import requests
import time
from botocore.exceptions import ClientError

dynamodb = boto3.client('dynamodb')
LEDGER_TABLE = "OmniHealth-Idempotency-Ledger"

def lambda_handler(event, context):
    patient_id = event.get('patient_id')
    correlation_id = event.get('correlation_id')
    
    # 1. GENERATE THE IDEMPOTENCY KEY
    # A unique fingerprint for this exact patient transfer attempt
    idempotency_key = f"{patient_id}#{correlation_id}"
    
    # Calculate TTL (24 hours from now in UNIX epoch)
    expiration_time = int(time.time()) + (24 * 3600)
    
    try:
        # 2. ATTEMPT TO ACQUIRE THE LOCK
        # attribute_not_exists ensures this write ONLY succeeds if the key isn't already there
        dynamodb.put_item(
            TableName=LEDGER_TABLE,
            Item={
                'IdempotencyKey': {'S': idempotency_key},
                'ExpirationTime': {'N': str(expiration_time)}
            },
            ConditionExpression='attribute_not_exists(IdempotencyKey)'
        )
        
        print(f"Lock acquired for {idempotency_key}. Proceeding with API call.")
        
        # 3. EXECUTE THE TRANSFER
        payload = {"patient_id": patient_id, "data": "clinical_bundle"}
        response = requests.post("https://emr.hospital-b.com/fhir/Bundle", json=payload, timeout=5)
        
        if response.status_code not in [200, 201]:
            # This triggers the "Catch" block in Step Functions (The Rollback)
            raise Exception(f"Hospital B rejected data: {response.text}")
            
        return {"status": "SUCCESS", "idempotency_key": idempotency_key}

    except ClientError as e:
        # 4. HANDLE THE DUPLICATE (The core of Idempotency)
        if e.response['Error']['Code'] == 'ConditionalCheckFailedException':
            print(f"Idempotency hit! {idempotency_key} was already processed.")
            # We safely return success without making the API call again, 
            # preventing a duplicate record in Hospital B.
            return {"status": "SKIPPED_DUPLICATE", "idempotency_key": idempotency_key}
        else:
            raise e

```

Because AWS Step Functions passes the JSON state from one step to the next, these functions will receive the exact `patient_id` and `correlation_id` that the core transfer Lambda used.

The Success Notification (Saga-Task-Notify-Hosp-A)

This function executes only if Hospital B successfully accepted the payload. It reaches back to Hospital A to officially close the loop, changing the local EMR status to `COMPLETED`.

```python
import json
import requests

def lambda_handler(event, context):
    # Step Functions passes the output of the previous step into this event
    # e.g., event = {"status": "SUCCESS", "idempotency_key": "123#abc", "patient_id": "123"}
    
    patient_id = event.get('patient_id', 'unknown')
    
    print(f"Executing Success Notification for Patient {patient_id}")
    
    try:
        # Callback to Hospital A to update the transfer status
        hospital_a_callback_url = f"https://emr.hospital-a.com/fhir/Transfer/{patient_id}/_status"
        
        # We tell Hospital A that the data safely reached Hospital B
        payload = {
            "status": "COMPLETED",
            "destination_ack": True
        }
        
        response = requests.patch(
            hospital_a_callback_url, 
            json=payload,
            headers={"Content-Type": "application/json"},
            timeout=5
        )
        
        if response.status_code not in [200, 204]:
            raise Exception(f"Hospital A failed to update status: {response.text}")
            
        return {"status": "NOTIFIED_SUCCESSFULLY"}

    except Exception as e:
        print(f"Error notifying Hospital A: {str(e)}")
        raise e

```

The Compensating Transaction (Saga-Rollback-Hosp-A)

This function executes *only* if the `TransferToHospitalB` step fails (e.g., Hospital B rejects the schema). Because Step Functions uses the `Catch` block with `ResultPath: "$.errorInfo"`, this Lambda receives the exact error message that caused the failure, allowing it to inform Hospital A exactly why the transfer was aborted.

```python
import json
import requests

def lambda_handler(event, context):
    # The Catch block in Step Functions injects the error details into the event payload
    patient_id = event.get('patient_id', 'unknown')
    error_details = event.get('errorInfo', {})
    
    error_message = error_details.get('Cause', 'Unknown failure at destination')
    
    print(f"Executing Compensating Rollback for Patient {patient_id}. Reason: {error_message}")
    
    try:
        # Callback to Hospital A to revert the transfer status
        hospital_a_callback_url = f"https://emr.hospital-a.com/fhir/Transfer/{patient_id}/_status"
        
        # We officially revert the state so Hospital A knows the patient data was NOT accepted
        payload = {
            "status": "FAILED_REJECTED",
            "failure_reason": error_message
        }
        
        response = requests.patch(
            hospital_a_callback_url, 
            json=payload,
            headers={"Content-Type": "application/json"},
            timeout=5
        )
        
        if response.status_code not in [200, 204]:
            # If the rollback fails, Step Functions marks the execution as FAILED,
            # alerting your engineers to manually fix the out-of-sync state.
            raise Exception(f"Rollback to Hospital A failed: {response.text}")
            
        return {"status": "ROLLBACK_COMPLETED"}

    except Exception as e:
        print(f"Error during rollback for Hospital A: {str(e)}")
        raise e

```

### Step 6: Step Functions ASL (The Saga Pattern)

This is the JSON definition for the Step Functions State Machine. It explicitly maps out the Compensating Transaction. If Hospital B rejects the data, it catches the error and routes the workflow to the Rollback Lambda, keeping both hospitals perfectly in sync.

```json
{
  "Comment": "OmniHealth Saga Orchestrator for Task 8 Patient Transfers",
  "StartAt": "TransferToHospitalB",
  "States": {
    "TransferToHospitalB": {
      "Type": "Task",
      "Resource": "arn:aws:lambda:ap-south-1:123456789012:function:Saga-Task-Transfer-Hosp-B",
      "Retry": [
        {
          "ErrorEquals": ["States.Timeout", "States.TaskFailed"],
          "IntervalSeconds": 2,
          "MaxAttempts": 3,
          "BackoffRate": 2.0
        }
      ],
      "Catch": [
        {
          "ErrorEquals": ["States.ALL"],
          "Next": "CompensatingRollbackHospitalA",
          "ResultPath": "$.errorInfo"
        }
      ],
      "Next": "NotifyHospitalASuccess"
    },
    
    "NotifyHospitalASuccess": {
      "Type": "Task",
      "Resource": "arn:aws:lambda:ap-south-1:123456789012:function:Saga-Task-Notify-Hosp-A",
      "Next": "CleanupStagedData",
      "ResultPath": null
    },
    
    "CleanupStagedData": {
      "Type": "Succeed"
    },
    
    "CompensatingRollbackHospitalA": {
      "Type": "Task",
      "Resource": "arn:aws:lambda:ap-south-1:123456789012:function:Saga-Rollback-Hosp-A",
      "Comment": "Updates Hospital A's EMR status from IN_PROGRESS to FAILED_REJECTED",
      "Next": "FailWorkflow"
    },
    
    "FailWorkflow": {
      "Type": "Fail",
      "Cause": "Saga Rollback Executed due to Hospital B rejection."
    }
  }
}

```
