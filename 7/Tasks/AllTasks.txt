Master Task List: Enterprise-Grade Cloud Architecture
This updated task execution flow integrates every Principal-level architectural enhancement (Saga patterns, Zero-Knowledge Proofs, AWS Private CA, Lambda Secret Caching, and Post-Quantum Cryptography) directly into the runtime logic. All infrastructure is deployed across Multi-AZ environments with Route 53 Resolver DNS Firewalls active in every VPC to block data exfiltration.


Task 1: OpenEMR A Website (Opened by Human)
 * Where it lives: Block 3 (Hospital A VPC).
 * The Flow: A doctor opens the URL. The request hits Hospital A's Public ALB using Hybrid Post-Quantum TLS 1.3 to secure data against future quantum decryption. The ALB's AWS WAF blocks malicious IPs, matches the UI path (/*), and triggers Amazon Cognito (Cognito-Pool-Hospital-A) for MFA login. Once authenticated, traffic routes into the private subnet to the OpenEMR A container (running on Multi-AZ ECS Fargate for high availability).
 * Endpoint: [https://emr.hospital-a.com](https://emr.hospital-a.com)



Task 2.1: Fetch Data from Fitbit / Google Health API (Cloud Deployment)
 * Where it lives: Block 2 (OmniHealth SaaS Hub VPC).
 * The Flow:
   * The React Native mobile app calls the Hub's Private API Gateway. API Gateway Usage Plans enforce Tenant-Aware Rate Limiting (preventing one hospital's users from crashing the Hub).
   * API Gateway validates the request against a strict JSON Schema Draft-07 Validator to drop malformed requests instantly, generates an X-Correlation-ID, and invokes FITBIT_FETCHER_LAMBDA.
   * The Lambda uses the AWS Parameters and Secrets Extension. It checks its local volatile RAM cache for Fitbit tokens. If missing (cache miss), it queries AWS Secrets Manager (decrypted via KMS CMK), caches the tokens locally with a 5-minute TTL to prevent API throttling, and routes outbound via the NAT Gateway (Static IP).
   * The Lambda rotates the refresh_token if needed, pulls the latest vitals, and computes a SHA-256 hash.
   * Any print() or logging statements in the Lambda are intercepted by a CloudWatch Logs Data Protection Policy, which automatically scrubs and redacts accidental PHI before writing to disk.
   * The Lambda writes a WORM audit receipt to S3 and returns the telemetry to the app.
 * Endpoints:
   * Hub Trigger: POST [https://api.omnihealth.com/fitbit/sync](https://api.omnihealth.com/fitbit/sync)
   * Fitbit OAuth / Health: POST [https://api.fitbit.com/oauth2/token](https://api.fitbit.com/oauth2/token)


Task 2.2: Post Fitbit Data from Mobile to OpenEMR A
 * Where it lives: Crosses Block 1 \rightarrow Block 2 \rightarrow Block 3.
 * The Flow:
   * The mobile app posts JSON vitals to the Hub's Public Ingest ALB. AWS WAF scrubs the payload and injects the X-Correlation-ID.
   * Mirth Connect (running Multi-AZ) translates JSON to FHIR R4 in-memory. Before queueing, it passes the payload through a strict HL7 FHIR Schema Validator. Malformed payloads are routed to a Quarantine queue.
   * Valid payloads are written to the Ephemeral S3 Staging Bucket. Mirth drops a pointer event into a Tenant-Specific Amazon SQS FIFO Queue (omnihealth-hosp-a.fifo). The queue uses MessageGroupId=Patient_ID to ensure strict chronological ordering per patient without head-of-line blocking for other patients.
   * SQS triggers OPENEMR_POST_LAMBDA via PrivateLink. The event mapping enforces Adaptive Backpressure (Concurrency Limit = 10) to ensure Hospital A's legacy database is never overwhelmed by cloud spikes.
   * The Lambda pulls OIDC tokens (via in-memory secret cache) and egresses via the NAT Gateway. It initiates a Mutual TLS (mTLS) handshake with Hospital A. The client certificates are automatically generated and rotated by AWS Private Certificate Authority (Private CA).
   * Upon receiving 201 Created from OpenEMR A, the Lambda issues s3:DeleteObject for the ephemeral file and logs the 7-Year WORM audit receipt.
 * Endpoints:
   * Ingest (Hub ALB): POST [https://ingest.omnihealth.com/fitbit](https://ingest.omnihealth.com/fitbit)
   * Egress (mTLS): POST [https://emr.hospital-a.com/fhir/Observation](https://emr.hospital-a.com/fhir/Observation)




Task 3: Bedside Monitor (BSM) Data to OpenEMR A
 * Where it lives: Block 1 \rightarrow Block 2 \rightarrow Block 3.
 * The Flow: Bedside monitors stream continuous HL7 telemetry over Post-Quantum TLS to the Hub ALB. Mirth validates the schema, stages large payloads ephemerally, and queues events in the Hospital A-specific SQS FIFO queue. OPENEMR_POST_LAMBDA executes with tenant concurrency caps, retrieves cached Secrets Manager tokens, exits via NAT Gateway, authenticates using AWS Private CA-backed mTLS, and writes to OpenEMR A.
 * Endpoints:
   * Ingest: POST [https://ingest.omnihealth.com/hl7](https://ingest.omnihealth.com/hl7)
   * Egress: POST [https://emr.hospital-a.com/fhir/Observation](https://emr.hospital-a.com/fhir/Observation)

Task 6: Vital Fetch in Omniviewer from OpenEMR A (Intra-VPC)
 * Where it lives: Strictly inside Block 3 (Hospital A VPC Private Subnet).
 * The Flow: Omniviewer needs to render patient vitals. Instead of leaving the VPC, it queries a Route 53 Private Hosted Zone (emr.internal.hospital-a.local), resolving to OpenEMR A's private IP. Using its IAM role, Omniviewer fetches a local service token from Hospital A's internal AWS Secrets Manager vault, authenticates, and fetches the data over the local subnet.
 * Endpoint: GET [https://emr.internal.hospital-a.local/fhir/Patient/123](https://emr.internal.hospital-a.local/fhir/Patient/123)



Task 7: From Omniviewer Generate AR/VR
 * Where it lives: Block 3 \rightarrow Block 2.
 * The Flow: Omniviewer hits the Hub API Gateway. API Gateway triggers ARVR_PROCESSOR_LAMBDA, which executes Blender mesh generation in-memory. The resulting USDZ file is encrypted via KMS CMK and saved to a dedicated asset S3 bucket, returning a secure pointer.
 * Endpoint: POST [https://api.omnihealth.com/arvr/generate](https://api.omnihealth.com/arvr/generate)




Task 8: Data Transfer from OpenEMR A to OpenEMR B (Saga Pattern & ZKP)
 * Where it lives: Block 3 (Hospital A) \rightarrow Block 2 (Hub) \rightarrow Block 3 (Hospital B).
 * The Flow:
   * OpenEMR A pushes a transfer bundle to the Hub ALB. Included in the header is a Zero-Knowledge Proof (zk-SNARK) mathematically verifying patient consent without revealing the patient's identity to OmniHealth.
   * Mirth stages the bundle in Ephemeral S3 and enqueues it in Hospital B's dedicated SQS FIFO queue.
   * SQS triggers an AWS Step Functions State Machine (The Saga Pattern) instead of a raw Lambda, ensuring distributed transaction safety.
   * Step Functions verifies the ZKP consent math. It then generates an Idempotency Key and stores it in Amazon DynamoDB.
   * It posts the bundle to Hospital B over mTLS (backed by Private CA). Hospital B uses the DynamoDB Idempotency Key in the header to ensure it never processes a duplicate record if a network retry occurs.
   * If Hospital B rejects it, the Saga executes a Compensating Transaction to notify Hospital A of the failure. If successful, it triggers the immediate Ephemeral S3 purge and WORM audit write.
 * Endpoints:
   * Ingest: POST [https://ingest.omnihealth.com/transfer](https://ingest.omnihealth.com/transfer)
   * Egress: POST [https://emr.hospital-b.com/fhir/Bundle](https://emr.hospital-b.com/fhir/Bundle)

Task 10: Data Transfer from OpenEMR B to OpenMRS
 * Where it lives: Block 3 (Hospital B OpenEMR) \rightarrow Block 2 \rightarrow Block 3 (OpenMRS).
 * The Flow: OpenEMR B pushes a sync payload to the Hub. Mirth stages it in S3 and queues it. SQS FIFO triggers an AWS Step Functions Saga to manage the transaction. The orchestration workflow fetches cached OpenMRS credentials, executes the transfer via NAT Gateway/mTLS, ensures DynamoDB idempotency, and immediately auto-purges the staged data upon a 200 OK response.
 * Endpoints:
   * Ingest: POST [https://ingest.omnihealth.com/mrs-sync](https://ingest.omnihealth.com/mrs-sync)
   * Egress: POST [https://openmrs.hospital-b.com/ws/rest/v1](https://openmrs.hospital-b.com/ws/rest/v1)




Task 12: IoT Water Quality Data to OpenEMR B
 * Where it lives: Block 1 (IoT) \rightarrow Block 2 \rightarrow Block 3 (Hospital B).
 * The Flow: IoT sensors push telemetry over TLS. The Hub API Gateway uses a JSON Schema to reject malformed packets at the edge. Mirth translates it, stages it, and uses SQS FIFO to trigger IOT_STORE_LAMBDA. The Lambda fetches OIDC tokens from its local in-memory cache, exits via the NAT Gateway, and posts the FHIR Observation to OpenEMR B using mTLS. CloudWatch Log Scrubbing ensures no telemetry details leak into server logs.
 * Endpoints:
   * Ingest: POST [https://ingest.omnihealth.com/iot/water](https://ingest.omnihealth.com/iot/water)
   * Egress: POST [https://emr.hospital-b.com/fhir/Observation](https://emr.hospital-b.com/fhir/Observation)



Task 13: Mobile App to See IoT Water Quality Data
 * Where it lives: Block 1 (Mobile) \rightarrow Block 2 (Hub) \rightarrow Block 3 (Hospital B API).
 * The Flow: The mobile app queries the Hub API Gateway. Because Block 2 is strictly Zero-PHI and holds no permanent database, IOT_DATA_FETCHER_LAMBDA fetches Hospital B's tokens from the Secrets Manager cache, routes outbound via the NAT Gateway, and queries OpenEMR B directly over mTLS. The Lambda logs a read-receipt in the WORM bucket and streams the JSON back to the mobile app instantly.
 * Endpoints:
   * Mobile Request: GET [https://api.omnihealth.com/iot/water/latest](https://api.omnihealth.com/iot/water/latest)
   * Target Fetch: GET [https://emr.hospital-b.com/fhir/Observation?code=water-quality](https://emr.hospital-b.com/fhir/Observation?code=water-quality)
