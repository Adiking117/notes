Passwordless Secret Retrieval: The Lambda activates. Using its IAM Execution Role, it calls AWS Secrets Manager. AWS KMS decrypts the secret using your Customer-Managed Key (CMK), handing the Lambda the client_id, client_secret, and current refresh_token.

Phase 1: Ingress & Perimeter Defense (Block 1 $\rightarrow$ Block 2 Edge)Mobile Client Dispatch: The mobile app formats the health payload fetched during Task 2.1 into an HTTPS POST request:Destination: POST [https://ingest.omnihealth.com/fitbit](https://ingest.omnihealth.com/fitbit)Headers: Content-Type: application/json, Authorization: Bearer <Mobile_App_Session_Token>Payload: Raw wearable metrics (steps, heart rate array, resting heart rate, device ID, UTC timestamps).

DNS & Edge Decryption: Amazon Route 53 resolves ingest.omnihealth.com to the Hub's public Application Load Balancer (ALB). 
The ALB terminates the public TLS 1.3 connection using an SSL certificate managed by AWS Certificate Manager (ACM).
WAF Scrubbing: AWS WAF inspects incoming packets against rulesets:Cross-Site Scripting (XSS) and SQL Injection (SQLi) filters.Rate-limiting per IP (mitigating volumetric DDoS).
Payload size restrictions (dropping any packet exceeding normal telemetry boundaries).
Distributed Trace Injection: As the packet passes through the ALB:An X-Correlation-ID (e.g., corr-fitbit-2026-98124a) and an AWS X-Ray trace header (X-Amzn-Trace-Id: Root=1-67...) are stamped into the HTTP headers.
This identifier stays attached to the data across every subsequent queue, Lambda, and API call.


Phase 2: In-Memory Transformation & Resilient Queuing (Block 2 Private Subnet)Handoff to Mirth Connect: 
The ALB routes the cleaned payload over an internal VPC path to Mirth Connect running on a private EC2 instance (which has no public IP).
Zero-Disk In-Memory Transformation:Under HIPAA and Saurabh's Zero-PHI guidelines, Mirth must never write this incoming payload to local EC2 storage or temporary log files.Mirth's internal JavaScript/Java channel maps the proprietary Fitbit JSON in volatile RAM directly into a standard HL7 FHIR R4 Observation Bundle:

}


Publishing to SQS FIFO: Mirth publishes this FHIR JSON payload into an Amazon SQS FIFO Queue (fitbit-observations.fifo).

Security: Mirth uses its AWS IAM Execution Role (Passwordless RBAC) to call sqs:SendMessage.

Encryption: The queue is encrypted at rest using an AWS KMS Customer-Managed Key (CMK).MessageGroupId: Set to the patient identifier (Patient-HOSP-A-94812). This guarantees that vitals for a given patient are processed in strict chronological sequence.
MessageDeduplicationId: Generated using a SHA-256 hash of the payload to prevent accidental double-posting if the mobile app retries.

Dead-Letter Queue (DLQ): Attached to catch and isolate any malformed message that fails processing after 5 attempts.


Phase 3: Serverless Invocation via PrivateLinkEvent Source Mapping: AWS Lambda monitors fitbit-observations.fifo. As soon as the message lands, AWS's internal event-source mapping invokes the OPENEMR_POST_LAMBDA.

PrivateLink Isolation: The Lambda resides inside the Hub’s Private Subnet. It receives its invocation payload through an AWS PrivateLink (Interface VPC Endpoint). 
The data never transits the public internet to reach the compute worker.

Context Propagation: The Lambda extracts the original X-Correlation-ID from the SQS message attributes and sets it as the active correlation tag for all its CloudWatch log entries.

Phase 5: Secure Egress & Hospital Ingestion (Block 2 $\rightarrow$ Block 3)

The Lambda now transmits the FHIR payload from the OmniHealth Hub into Hospital A's network.

1. Outbound Routing via Network Firewall & NAT Gateway
The Lambda sends an HTTPS request to [https://emr.hospital-a.com/fhir/Observation](https://emr.hospital-a.com/fhir/Observation).

The subnet's route table points outbound traffic (0.0.0.0/0) to the AWS Network Firewall.

Stateful Domain Filtering: The firewall verifies that the target domain is explicitly present on the outbound whitelist (emr.hospital-a.com). 
Any unauthorized destination is dropped.

Source IP Translation: The traffic passes to the AWS NAT Gateway in the public subnet. 
The NAT Gateway strips the Lambda's private IP and stamps the packet with OmniHealth's dedicated Static Elastic IP (EIP).


2. The Multi-Layered Handshake at Hospital A's ALB
When the packet hits Hospital A's public ALB, three verification gates execute in sequence:

Network Layer — IP Whitelist: Hospital A’s security group evaluates the incoming packet's source IP. If it does not match OmniHealth’s NAT Gateway Static Elastic IP, the connection is dropped immediately.

Transport Layer — Mutual TLS (mTLS): Standard HTTPS only validates the server. Here, Hospital A's ALB requests an identity certificate from the client.
The Lambda presents an X.509 Client Certificate stored securely in its execution environment.
Hospital A's ALB validates this certificate against its internal trusted Certificate Authority (CA) trust store.

Application Layer — Path-Based Routing (Bypassing Cognito):Human browser requests to /* are redirected by the ALB to Amazon Cognito for MFA login.Because the Lambda's request targets /fhir/Observation and presents an Authorization: Bearer <token> header, the ALB's path-based listener rule evaluates:$$\text{Path} = \texttt{/fhir/*} \implies \text{Action} = \textbf{Forward to Target Group (Bypass Cognito)}$$


3. Execution on Hospital A EC2
The ALB forwards the packet to Hospital A's private EC2 instance.
Nginx Reverse Proxy: Terminates the internal ALB connection and routes port 443 traffic internally to OpenEMR's API engine.
Token Verification: OpenEMR validates the Bearer token's signature, scope (observation:write), and expiration against its internal authentication database.
Database Write: OpenEMR writes the heart rate records to the dedicated Amazon RDS (MySQL) instance.

Response: OpenEMR responds with HTTP 201 Created (including the assigned FHIR resource ID: Observation/obs-9021).

Step 1: Ingress & Traceability Stamp
The Action: Hospital A’s OpenEMR initiates a patient data transfer bundle, sending it over an encrypted mTLS connection to the OmniHealth Hub: POST [https://ingest.omnihealth.com/transfer](https://ingest.omnihealth.com/transfer).

The Mechanics: The Hub's ALB and AWS WAF inspect the packet, verify the mTLS client certificate, and stamp the request with an X-Correlation-ID via AWS X-Ray. This tracking ID will follow the packet through every single subsequent hop.

Step 2: Mirth In-Memory Processing & Ephemeral S3 Staging (The Claim-Check Pattern)
The Action: Mirth Connect receives the payload. Because large medical files exceed the size limits of message queues, Mirth uses the Claim-Check Pattern:

Mirth writes the raw encrypted transfer payload into the Amazon S3 Ephemeral Staging Bucket (encrypted at rest using an AWS KMS Customer-Managed Key).

Mirth immediately publishes a lightweight event message (the "claim check" pointer, e.g., {"s3_bucket": "omnihealth-staging", "key": "bundle-9982.json"}) into the Amazon SQS FIFO Queue (hospital-transfer.fifo).

The Mechanics: The SQS FIFO queue uses a Message Group ID to guarantee strict delivery order (ensuring updates for a patient arrive in the exact sequence they were sent). A Dead-Letter Queue (DLQ) is attached to catch failed messages if Hospital B's server goes down.

Step 3: Triggering Serverless Compute via PrivateLink
The Action: The SQS FIFO queue automatically triggers the FHIR_POST_LAMBDA.

The Mechanics: The Lambda wakes up inside the private subnet, invoked privately via an AWS PrivateLink (Interface VPC Endpoint). It retrieves the S3 pointer from the queue message and uses its passwordless IAM Execution Role to download the staged bundle from S3 into its secure, volatile RAM.

Step 4: Zero-Trust Outbound Delivery to Hospital B
The Action: The Lambda prepares to send the data to Hospital B (POST [https://emr.hospital-b.com/fhir/Bundle](https://emr.hospital-b.com/fhir/Bundle)).

The Mechanics:

Token Retrieval: Using its IAM role, the Lambda queries AWS Secrets Manager to fetch Hospital B's full credential bundle (client_id, client_secret, access_token, refresh_token), refreshing the OIDC token dynamically if expired.

Egress Perimeter: The packet routes through the AWS Network Firewall (validating destination allow-lists) and exits via the AWS NAT Gateway, stamping the packet with OmniHealth's dedicated Static Elastic IP.

mTLS Handshake: The Lambda connects to Hospital B's ALB over mTLS, presenting its X.509 client certificate and passing the fresh OAuth Bearer token. Hospital B validates everything, processes the bundle, and responds with HTTP 200 OK.

Step 5: Immediate Auto-Purge & Immutable WORM Auditing (The Settlement)
The Action: The exact millisecond the Lambda receives 200 OK from Hospital B, execution triggers two final settlement tasks:

Immediate Ephemeral Deletion: The Lambda issues an s3:DeleteObject call against the temporary file it downloaded from in Step 2. Coupled with a 24-hour S3 Lifecycle auto-purge rule, this guarantees zero PHI retention in Block 2.

WORM Compliance Proof: The Lambda writes a tamper-proof, non-PHI audit receipt into the Immutable S3 Audit Bucket (7-Year S3 Object Lock in Compliance Mode).

What the Audit Receipt Proves: It contains zero patient names and zero medical data. It logs only technical proof: the Correlation_ID, Source: Hospital_A, Target: Hospital_B, a SHA-256 hash of the payload, Staging_Data_Purged: True, and the exact timestamp. This immutable receipt satisfies HIPAA § 164.312(b) audit controls for the next 7 years.

Task 13: Mobile App to See IoT Water Quality Data (Fetches from Hospital B API — Zero S3 Reads!)
Where it lives: Block 1 (Mobile App) → Block 2 (OmniHealth Hub Proxy) → Block 3 (Hospital B OpenEMR API).

The Flow: Because Block 2 enforces strict Zero-Data Retention (all staged S3 files are auto-purged in Task 12), the mobile app never reads from an S3 bucket. Instead:

A user opens the React Native app, which calls the Hub API Gateway (GET [https://api.omnihealth.com/iot/water/latest](https://api.omnihealth.com/iot/water/latest)), generating an X-Ray Correlation-ID and invoking IOT_DATA_FETCHER_LAMBDA via AWS PrivateLink.

Using its Passwordless IAM Execution Role, IOT_DATA_FETCHER_LAMBDA retrieves Hospital B's credentials and OIDC tokens from AWS Secrets Manager, refreshing the access token if needed.

The Lambda exits through the AWS Network Firewall and AWS NAT Gateway (Static Elastic IP) over mTLS to query Hospital B's OpenEMR B FHIR API directly (GET [https://emr.hospital-b.com/fhir/Observation?code=water-quality](https://emr.hospital-b.com/fhir/Observation?code=water-quality)).

Hospital B returns the latest water quality FHIR Observations from its RDS database; the Lambda logs a non-PHI access receipt in the Immutable S3 Audit Bucket (WORM) and streams the clean JSON back to the mobile app.
